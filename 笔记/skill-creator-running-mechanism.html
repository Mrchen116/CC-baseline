Anthropic skill-creator

skill-creator 运行机制拆解：把 skill 当成可评估的工程资产

skill-creator 不是简单的模板生成器。它更像一条围绕 skill 的小型 CI 流水线： 先定义触发意图，再写 SKILL.md，然后用测试提示词、基线对照、评分器、HTML 审阅器和 description 优化器不断迭代。

一、先给结论：它不是模板生成器，而是 skill 的 CI 流水线

普通的 prompt 工程通常止步于“写一段更好的说明”。skill-creator 的思路更工程化： 把 skill 看成一个可以被触发、执行、评测、对照、复盘、再发布的能力模块。

创建 先问清楚 skill 要解决什么任务、什么时候触发、输出格式是什么、成功标准是什么。
评测 对同一批 eval 同时跑 with-skill 和 baseline，再用 grader、benchmark、viewer 判断是否真的变好。
优化 根据人类反馈和失败样本修改 SKILL.md、脚本、示例和 description，进入下一轮 iteration。

如果把普通 prompt 看成“手写操作说明”，skill 更接近“带文档、脚本、测试、发布包的能力模块”。 这也是它最像深度学习调参的地方：eval set 是数据集，assertions 是监督信号，with-skill/baseline 是消融实验， viewer 是人工标注界面，description 优化则像一个小型路由分类器实验。

二、先看全局：skill-creator 的完整闭环

在拆 eval、grader、description 优化之前，先看整张地图。主流程是： 先产出一个可测试的 skill，再用评估循环打磨能力质量，最后优化 description 的触发边界并打包发布。

三、源码目录地图：每个文件支撑流程图里的哪一段

这个目录本身是全局地图，不属于 A 阶段。更准确的理解是： SKILL.md 是总控剧本，scripts/ 是自动化执行器， agents/ 是评审角色，references/ 定义数据协议， eval-viewer/ 和 assets/ 负责把结果交给人审。

文件 对应阶段 作用
SKILL.md A/B/C/D 横跨 定义 skill-creator 的完整协作流程：创建 skill、跑 eval、收集反馈、优化 description、打包发布。
references/schemas.md B Evaluate 定义 evals.json、grading.json、benchmark.json 等数据结构，保证脚本和 viewer 能对齐。
agents/grader.md、agents/analyzer.md、agents/comparator.md B Evaluate 提供评分、分析和盲评角色，用来把输出结果转成可讨论的质量信号。
scripts/aggregate_benchmark.py B Evaluate 把每个 run 的 grading.json 和 timing.json 聚合成 pass rate、耗时、token 的 benchmark。
eval-viewer/generate_review.py、eval-viewer/viewer.html B Evaluate 生成可交互 HTML，让用户并排看 with-skill 和 baseline 的产物、指标、反馈入口。
assets/eval_review.html C Trigger 让用户审阅 should-trigger / should-not-trigger 查询集，导出 description eval set。
scripts/run_eval.py、scripts/improve_description.py、scripts/run_loop.py C Trigger 检测 description 是否触发、根据失败样本改写 description，并用 train/test split 选择最佳版本。
scripts/quick_validate.py、scripts/package_skill.py D Ship 发布前做结构校验，并把最终 skill 打成 .skill 包。

四、A Draft：把想法变成一个可测试的 skill

Draft 阶段不是直接写一大段提示词，而是先把 skill 的边界问清楚： 什么时候触发，输入是什么，输出是什么，是否需要脚本、模板、示例文件，以及怎样才算成功。 

---
name: invoice-extractor
description: Use this skill when the user needs to extract structured fields from vendor invoices, normalize currencies, and produce a CSV for accounting review.
---

# Invoice Extractor

Use this workflow when the user gives invoice PDFs, screenshots, or spreadsheets and asks for structured accounting data.

1. Inspect every input file.
2. Extract vendor, invoice number, date, amount, tax, currency, and missing fields.
3. Produce a CSV and a short review note.
4. Use bundled scripts when available instead of hand-rolling parsing logic.
图 2：Skill 的三层加载

第一层只有 name 和 description，它决定是否打开 skill。第二层是主说明，第三层是脚本、模板和示例。

五、B Evaluate：先证明 skill 真的有用

这个阶段的核心问题不是“skill 看起来是不是专业”，而是“同样的任务，用 skill 是否真的更好”。 因此每个测试用例都要跑两遍：一遍带 skill，一遍作为 baseline。

eval set 是怎么生成的

eval set 不是凭空写出来的。SKILL.md 要求写完 skill draft 后，先提出 2-3 个真实测试 prompt 给用户确认。 用户确认后保存到 evals/evals.json。初始文件主要包含 prompt、expected_output 和输入文件路径， assertions 可以在 run 进行时补充。

图 3：eval set 的生成过程

eval set 的来源是用户真实任务，而不是抽象题目。后续所有 with-skill/baseline 都围绕这批任务展开。 

{
  "evals": [
    {
      "id": 1,
      "name": "vendor-tax-csv",
      "prompt": "读取 Downloads/invoices 里的三张供应商发票 PDF，输出 vendor、invoice_no、date、amount、tax、currency 六列 CSV。",
      "expected_output": "生成可被财务复核的 CSV，并标出缺失字段。",
      "files": ["evals/files/vendor-a.pdf", "evals/files/vendor-b.pdf", "evals/files/vendor-c.pdf"],
      "expectations": []
    }
  ]
}

一次 eval 为什么要跑两条线

图 4：一次 eval 为什么要跑两条线

这是控制变量实验：prompt 和输入文件相同，变量只有一个，即是否让 Claude 使用当前 skill。

两套启动方式不要混淆。

能力质量评测不是通过命令行重新跑 claude -p，而是由正在使用 skill-creator 的主控 agent 直接启动 subagent：一个 subagent 走 with_skill，另一个 subagent 走 baseline。 这个设计有一个重要边界：被测 run 已经运行在 subagent 里，因此如果某个 skill 的核心能力依赖“再开 subagent”来完成， 这条评测路径不能真实复现嵌套调度。

评测对象 启动方式 真正测什么 天然不擅长什么
能力质量 eval 主控 agent 启动 with-skill / baseline subagents 同一任务下，当前 skill 是否让最终产物更好、更稳定，成本是否可接受。 依赖再次启动 subagent 的 skill。被测 run 已经是 subagent，不能再开子 subagent，因此无法真实评估 orchestrator 型 skill 的调度质量。
description 触发 eval scripts/run_eval.py 调用命令行 claude -p 某条用户 query 是否会触发这个 skill，是否误触发或漏触发。 skill 触发以后做得好不好，以及多轮对话过程质量。

评估目录是后续工具的协议

invoice-extractor-workspace/                  # 这个 skill 的评估工作区
└── iteration-1/                              # 一轮实验批次
    ├── eval-vendor-tax-csv/                 # 一个具体测试用例
    │   ├── eval_metadata.json               # eval id、名称、prompt、assertions
    │   ├── with_skill/                      # 实验组：使用当前 skill
    │   │   ├── outputs/                     # 最终产物，如 invoice.csv
    │   │   ├── transcript.md                # 执行过程，grader 会读
    │   │   ├── timing.json                  # token 和耗时
    │   │   └── grading.json                 # grader 对 assertions 的判分
    │   └── without_skill/                   # 对照组：不用 skill 或旧 skill
    │       ├── outputs/
    │       ├── transcript.md
    │       ├── timing.json
    │       └── grading.json
    ├── benchmark.json                       # 机器可读聚合指标
    └── benchmark.md                         # 人类可读聚合报告
eval_metadata.json 这个 eval 是什么：id、名称、prompt、assertions。
outputs/ 真正给用户看的产物，也是 viewer 的核心内容。
transcript.md 执行过程证据。grader 不能只相信执行者声称完成了。
timing.json subagent 完成通知里的 token 和耗时，只出现一次，所以要及时保存。

六、B Evaluate：grader、benchmark、viewer 三层判断

skill-creator 不把“模型说自己完成了”当成成功。它把评估拆成三层： grader 看断言，benchmark 看整体指标，viewer 让人类看最终产物。

图 5：从产物到决策的三层判断

这三层回答不同问题：grader 问“断言过了吗”，benchmark 问“整体是否比 baseline 好”，viewer 问“人真的满意吗”。 

{
  "expectations": [
    {
      "text": "CSV 包含 vendor、invoice_no、date、amount、tax、currency 六列",
      "passed": true,
      "evidence": "outputs/invoice.csv header contains all required columns"
    },
    {
      "text": "缺失税号的发票必须标记 missing_tax_id",
      "passed": false,
      "evidence": "vendor-b row leaves the field blank without an explicit missing marker"
    }
  ],
  "summary": "Most extraction fields are correct, but missing-field handling is inconsistent."
}

benchmark 不是为了证明 with-skill 永远更好，而是为了量化取舍。一个 skill 可能用更多 token 和时间， 但换来更高通过率；也可能输出更漂亮，但断言没有提升。这些差异需要和用户一起判断。

图 6：viewer 不是展示页，而是下一轮输入采集器

七、C Trigger：description 优化器测的是路由

前两节测的是“skill 被使用以后做得好不好”。第七节测的是另一个问题： 这个 skill 到底该不该被唤起。这里的核心对象是 frontmatter 里的 description。

图 7：description 是 skill 的路由规则

description 不是给人看的简介，而是模型决定“要不要打开这个 skill”的路由信号。

触发 eval 的样本长什么样

description eval query 要像真实用户会输入的话，包括上下文、文件名、业务目的、模糊表达、错别字和近似但不该触发的负样本。 负样本不能太容易，否则只能证明 description 没有离谱，不能证明边界写得好。 

[
  {
    "query": "我老板刚发了一个 Q4 sales final FINAL v2.xlsx，让我加一列 profit margin，收入在 C 列，成本在 D 列",
    "should_trigger": true
  },
  {
    "query": "帮我解释一下 profit margin 是什么意思",
    "should_trigger": false
  },
  {
    "query": "我有几张 PDF 发票，想快速看一下总金额",
    "should_trigger": false
  }
]

run_eval.py 如何判断“触发了”

scripts/run_eval.py 的做法不是让模型自我报告“我会不会触发”，而是跑一次真实的 claude -p。注意这和第五节的能力质量 eval 是两条路径；这里不启动 with-skill/baseline subagents， 也不评最终产物，只观察路由是否命中。

图 8：run_eval.py 的触发检测机制

run_loop.py 如何避免 description 背题

如果只拿同一批 eval 不断优化，description 会越来越像那 20 条样本的关键词集合。 run_loop.py 会把 eval set 分成 train 和 held-out test：优化模型只根据 train 失败样本改写； 最终采用哪版 description，则看 test 分数。

八、D Ship：校验和打包成 .skill 文件

发布前会跑 quick_validate.py，检查 SKILL.md frontmatter 是否合规： 必须有 name 和 description，name 要是 kebab-case，description 不能包含尖括号且长度受限。

package_skill.py 会把最终 skill 打成 .skill 包，同时排除开发资产，例如 evals/、缓存文件和临时文件。这个选择很合理：eval 是开发过程资产，不一定要随最终能力包分发。

九、这个方案的局限性

Anthropic 这套方案强在把 skill 变成可评估的工程对象，但它不是万能测试框架。它默认最适合“单次任务执行型 skill”： 用户给一个 prompt，模型完成任务，产出文件或文本，然后 grader 和 viewer 评估结果。

局限 1：它不是多轮对话 harness。

对 SDD、需求澄清、访谈型 skill 来说，核心质量在多轮追问策略：是否先澄清、问什么、何时停止、如何根据用户回答更新需求状态。 当前 eval schema 主要是一个 prompt 加可选文件，不原生模拟“用户回答第二轮、第三轮”的过程。

局限 2：它不能真实评估嵌套 subagent 调度。

能力质量 eval 本身通过 subagent 执行 with-skill/baseline。由于 subagent 不能再开 subagent， 如果被测 skill 的核心是 orchestrator，例如需求澄清后分派多个专家 agent、项目管理 agent、TDD worker， 默认 creator eval 只能评最终近似结果，不能真实复现内部调度。

因此更准确的结论是：skill-creator 能很好评估“用了 skill 后结果是否更好”， 但不擅长评估“skill 内部的交互策略或 agent 调度策略是否更好”。

十、它体现的几个工程原则

原则 在 skill-creator 里的体现
把触发当路由问题 description 是 primary trigger mechanism，所以有独立的 should-trigger / should-not-trigger eval、近似负样本和 train/test holdout。
用 baseline 控制自嗨 同一 prompt 跑 with-skill 和 baseline，避免只看“用了 skill 后看起来不错”。
用人工反馈弥补指标盲区 viewer 让用户直接看最终产物，并把反馈写回下一轮优化。
把重复劳动沉淀成资源 如果 eval transcript 中反复出现同类 helper script，说明应该沉淀到 skill 的 scripts/。
防止过拟合 eval 改进 skill 时要求从反馈中泛化；description 优化也用 held-out test 选择最佳版本。
