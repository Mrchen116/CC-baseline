Anthropic · skill-creator

skill-creator 运行机制：谁在跑什么、什么时候跑

skill-creator 不是一段 prompt 模板，而是一套"主 agent 加多个 subagent + 几个 Python 脚本" 的协作流程。本笔记的目标是：让一个熟悉 Claude Code agent 但没读过这个 skill 源码的读者， 顺着读下来能搞清楚——每一步是谁在执行、何时被触发、读什么文件、写什么文件。

1 · 先把"谁是谁"理清楚

整个流程里出现的"agent / 脚本"分成三类。所有看起来神秘的 grader / analyzer / comparator 其实都是 主 agent 用 Task 工具临时派出去的 subagent，它们的"系统提示词"就是 agents/*.md 那几个文件里的内容； 描述优化阶段又有一组完全不同的角色，它们是 Python 脚本通过 claude -p subprocess 跑起来的独立 Claude 进程， 和 Task subagent 没有关系。

① 主 Agent（当前 Claude Code 会话）

用户在 Claude Code 里说"帮我做一个 skill"，触发了 skill-creator 这个 skill。当前这个会话就成为主 agent。 它把 SKILL.md（32K）当剧本读，按里面写的步骤推进流程：跟用户访谈、写 draft、生成 eval 文件、派 subagent、跑脚本、汇报结果。

剧本：SKILL.md身份：当前 Claude Code 会话触发：用户调用 /skill-creator

② Task Subagent（主 agent 用 Task 工具派出去的临时子会话）

主 agent 在评测阶段会派出四种角色的 subagent。每个 subagent 是一个独立的 Claude 进程，带着主 agent 写在 Task 工具 prompt 里的指令启动， 执行完一次性返回结果。agents/grader.md / analyzer.md / comparator.md 是给主 agent 看的—— 主 agent 读完后，把里面的"Role / Process / Output Format"原样塞进 Task 调用的 prompt 里，subagent 才会按那套规则行事。

角色啥时候被派读什么 / 写什么
Executor（with_skill / baseline） B 阶段 Step 1：对每个 eval case，主 agent 在同一个 turn 里成对派出 读 eval prompt + skill path；写 outputs/ + transcript
Grader B 阶段 Step 4：所有 executor 跑完后，对每个 run 派一个（也可以主 agent 自己 inline 打分） 读 agents/grader.md（作为指令）+ transcript + outputs；写 grading.json
Analyzer（benchmark 模式） B 阶段 Step 4：benchmark 聚合完成后派一个 读 agents/analyzer.md 的 "Analyzing Benchmark Results" 段 + benchmark.json；写 notes 数组
Comparator + Analyzer（post-hoc 模式） 可选高级流程：用户要做盲评 A/B 时 读 agents/comparator.md / analyzer.md + 两份 output；先盲判赢家，再分析为什么赢

③ Python 脚本 + claude -p subprocess（C 阶段专用）

描述优化阶段不用 Task subagent。它是主 agent 在 Bash 里跑 python -m scripts.run_loop， 这个脚本内部并发派出几十个 claude -p <query> subprocess（每个都是一个独立的 Claude Code 进程）， 专门检测某个 description 会不会触发这个 skill。这套机制和 Task subagent 完全独立。

脚本：scripts/run_loop.py底层：subprocess.Popen("claude -p ...")并发：ProcessPoolExecutor
结论先讲： 笔记里之后出现 "Grader 跑了"" Analyzer 跑了" 这种描述，意思都是 主 agent 在那一步用 Task 工具开了一个 subagent，把 agents/<name>.md 里的内容当 prompt 塞进去。 Grader / Analyzer / Comparator 不是常驻进程，也不是 cron 调度的——它们就是一次性的 Task 调用。

4 · A · Draft 阶段

这一段全部由主 agent 直接做，没有 subagent，没有脚本。

主 agent访谈用户，捕获意图

SKILL.md 给主 agent 列了 4 个必问问题：① 这个 skill 让 Claude 能做什么 ② 应该在什么用户语境/措辞下触发 ③ 输出格式是什么 ④ 要不要配测试用例（客观可验证的任务推荐配，主观风格类的不一定要）。如果对话里已经出现过用户想沉淀的工作流，主 agent 会先从历史里把这些字段抽出来再补问。

主 agent写 SKILL.md draft

name（kebab-case，≤64 字符）、description（≤1024 字符；SKILL.md 明确说当前 Claude 倾向于欠触发，让主 agent 把描述写得稍微"pushy"一点）、SKILL.md body（≤500 行；超了就拆 references/）。

主 agent提 2-3 个测试 prompt 并让用户确认

不写 assertions，先把 prompt 和期望输出存进 evals/evals.json。assertions 推迟到 B 阶段 Step 2 等 executor 在跑的时候再起草——这样主 agent 不会卡在等 IO 上。

{
  "evals": [
    {"id": 1, "prompt": "...", "expected_output": "...", "files": []}
  ]
}

5 · B · Evaluate 阶段（核心）

SKILL.md 把这一段标为 "one continuous sequence — don't stop partway through"。 主 agent 会沿着 Step 1 → 5 一路推到 viewer 打开为止。每一步都会落盘到 <skill-name>-workspace/iteration-N/eval-X/ 这个目录结构里。

Step 1 · 同一个 turn 内并行派出 2N 个 Executor subagent

Subagent · Executor × 2N

为什么必须同 turn 派出：SKILL.md 强调"don't spawn the with-skill runs first and then come back for baselines later"。原因是同 turn 派出去的 Task 才会真正并行，否则 wall clock 会被串行化拉爆。

派的方式：主 agent 在一个回复里连续调用 Task 工具 2N 次。每次的 prompt 是一段固定模板：

Execute this task:
- Skill path: <path-to-skill>   ← baseline 这行删掉就是 baseline
- Task: <eval prompt>
- Input files: <eval files>
- Save outputs to: <workspace>/iteration-N/eval-X/with_skill/outputs/
- Outputs to save: <用户关心的产物，如 "the .docx file">

baseline 是什么：新建 skill 时 baseline = 不带 skill 跑同样的 prompt；改进现有 skill 时，主 agent 先 cp -r 把旧版 skill 快照到 skill-snapshot/，baseline subagent 指向那个快照。

executor 干什么：就是一个普通 Claude Code subagent，按 prompt 完成任务，把产物写到指定目录，把执行过程作为 transcript 留下。它不知道自己是"with skill"还是"baseline"。

Step 2 · 等待期间，主 agent 起草 assertions

主 agent

2N 个 subagent 都在后台跑（可能几十秒到几分钟），主 agent 不空等。它给每个 eval case 起草一组客观可验证的判分项（如"输出 CSV 有 6 列"、"文件名是 invoices.csv"、"包含 vendor 字段"），写回 eval_metadata.json 的 assertions 数组。SKILL.md 提醒：主观质量项不要硬塞 assertion，留给人审。

Step 3 · 接收 timing notification 并立即落盘

主 agent

每个 Task subagent 完成时，Claude Code 会给主 agent 一条 notification，里面带 total_tokens 和 duration_ms——这是唯一能拿到这两个数的地方。主 agent 必须在收到通知的当下就把它写进对应 run 目录的 timing.json，否则数据就丢了。

Step 4 · Grade → Aggregate → Analyze

4a. 对每个 run 派一个 Grader subagent

Subagent · Grader × 2N

什么时候触发：所有 executor 跑完后，主 agent 为每个 run 目录派一个 Task。也可以 inline 自己打分（小 skill 常用），但 SKILL.md 默认推荐 subagent 模式。

主 agent 怎么调用：读完 agents/grader.md，把里面的 8 步流程（"读 transcript → 检查 output 文件 → 对每条 assertion 找证据 → 提取并验证隐式断言 → 读 user_notes.md → 评 eval 本身 → 写 grading.json"）作为 prompt 派给 subagent，附上 expectations、transcript_path、outputs_dir 三个参数。

grader 干什么：对每条 assertion 给出 {text, passed, evidence} 三元组——viewer 强依赖这三个字段名，写错就显示不出来。它还会做两件不显眼但关键的事：

  • extract claims：从 transcript 里抠出隐式断言（"我用了 pypdf 填表"）并验证，抓 executor 自己声称做了但实际没做的情况
  • critique the evals：如果某条 assertion "文件名对就算 pass" 但内容明显错了，grader 会在 eval_feedback 字段里报告——这条 assertion 太弱

4b. Bash 跑聚合脚本

Bash · aggregate_benchmark.py

主 agent 跑：

python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>

脚本扫所有 eval-*/{with_skill,without_skill}/run-*/grading.json，按 configuration 分组算 mean / stddev / min / max（pass_rate / time_seconds / tokens 三个指标），输出 benchmark.json + benchmark.md。delta = 第一个 configuration 减第二个，例如 +0.50 pass_rate, +13.2s, +8400 tokens。

4c. 派 Analyzer subagent 做模式分析

Subagent · Analyzer（benchmark 模式）

什么时候触发：benchmark.json 写完之后。主 agent 把 agents/analyzer.md 里 "Analyzing Benchmark Results" 那一节作为 prompt 派出去。

analyzer 干什么：它不提改进建议（那是 improvement 步骤的事），只在数据里捞模式：哪条 assertion 在 with/without 都满分（不区分能力）、哪条 eval 方差大（可能 flaky）、哪条 without_skill 永远失败但 with_skill 永远成功（强信号），token / time 是否被 skill 拉高了。输出是 JSON 数组的自由文本 note，会被插回 benchmark.json 的 notes 字段。

Step 5 · 启动 viewer，把球踢给用户

Bash · eval-viewer/generate_review.py

主 agent 在后台启 HTML viewer：

nohup python <skill-creator>/eval-viewer/generate_review.py \
  <workspace>/iteration-N \
  --skill-name "my-skill" \
  --benchmark <workspace>/iteration-N/benchmark.json \
  > /dev/null 2>&1 &

viewer 有两个 tab：Outputs（按 eval 翻页看 with-skill / baseline 产物 + 反馈框）和 Benchmark（pass rate / 时延 / token 的表格 + analyzer notes）。用户点 "Submit All Reviews"，所有反馈进 feedback.json。

用户

用户翻 viewer，在每个 eval 的反馈框里写自由文本（"图表缺坐标轴标签" / "完美" / 留空表示 ok），最后提交。Cowork 等无显示环境用 --static 出 HTML 文件让用户自己下载打开。

Step 6 · 读 feedback，改 SKILL.md，进 iteration-N+1

主 agent

主 agent 读 feedback.json，结合 benchmark + analyzer notes 想"该怎么改 SKILL.md"。SKILL.md 这一段写得很务实：不要 overfit 到这几个 case；保持 prompt 精简，砍掉没在产出价值的句子；少写 ALWAYS / NEVER，多写 why；如果几个 case 都让 executor 临时写了同一种 helper script，那是个把它打包进 scripts/ 的信号。

改完后把整个 B 阶段（Step 1 → 5）重跑一遍到 iteration-N+1/。generate_review.py 这次带 --previous-workspace，viewer 会把上一轮的 output 和 feedback 折叠显示作为对比。

可选：Advanced 盲评流程

Subagent · Comparator + Analyzer（post-hoc 模式）

当用户问"新版到底比旧版好吗"时，可以走这条更严谨的路：主 agent 先派一个 Comparator subagent，给它两份 output 标签 A / B（不告诉哪个是新版），让它生成 rubric 打分选赢家；再派一个 Analyzer（post-hoc 模式，读 analyzer.md 前半段），unblind 后分析"赢的那版到底赢在哪、输的那版改什么才能反超"，输出带优先级的 improvement_suggestions。

注意 analyzer.md 这一个文件里其实塞了两套指令：前半段是 post-hoc"为什么赢"，后半段（从 "Analyzing Benchmark Results" 起）是 "在 benchmark 里找模式"。主 agent 根据当前场景只把对应那一段贴进 prompt。

6 · C · Description Optimization 阶段

关键区别： 这一段不派 Task subagent，完全靠 Python 脚本 + claude -p subprocess。 因为要测的是"description 写成这样会不会让另一个全新的 Claude Code 会话把这个 skill 加载起来"—— 只有 claude -p（一个独立的、不知道当前会话上下文的 Claude Code 进程）才能模拟"陌生 Claude 看到 skill 列表"的状态。

Step 1 · 主 agent 生成 20 条 trigger eval query

主 agent

10 条 should-trigger（不同措辞、不同正式度，有用户不显式说技术名词的情况），10 条 should-not-trigger（关键在近似词陷阱——共享关键词但其实需要别的工具的 query）。SKILL.md 给了反面例子："Write a fibonacci function" 当作 PDF skill 的负例毫无价值，因为太显然不会触发。要的是临界样本。

Step 2 · 用户在 HTML 里审 query 集

主 agent + 用户

主 agent 把 assets/eval_review.html 模板里的 __EVAL_DATA_PLACEHOLDER__ 等占位符替换成实际数据，写到 /tmp/eval_review_<skill>.html 并 open 它。用户在网页里改 query、改 should_trigger 标签，点 "Export Eval Set"，下载到 ~/Downloads/eval_set.json。

Step 3 · 主 agent 启 run_loop.py 后台跑 5 轮

Bash · scripts/run_loop.py 
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <当前会话用的 model id> \
  --max-iterations 5 --verbose

这里有个细节：--model 必须传"当前 Claude Code 会话正在用的那个 model id"。理由是触发逻辑本来就是 model-specific 的——你 Opus 上调好的 description 给 Haiku 用可能 trigger 行为完全不一样。

run_loop.py 主循环：

  1. 切分 eval set：60% train + 40% test（按 should_trigger 分层洗牌，固定 seed=42 保证可复现）。test 集对 improvement 模型保密，避免 overfit。
  2. 本轮 evaluate：调 run_eval()，ProcessPoolExecutor 并发 10 个 worker，对 train+test 一起跑。每个 query 跑 runs_per_query=3 次取均值。
  3. 判 pass / fail：trigger_rate ≥ 0.5 视为"会触发"。和 should_trigger 比较得到 pass/fail。
  4. 如果 train 全 pass 或到第 5 轮：退出。
  5. 否则调 improve_description()：把当前 description、失败样本、所有历史 attempt（test 分数被刻意去掉，模型只看到 train 分数）打包成一个 prompt，调一次 claude -p 让它写新 description。
  6. 选 best：5 轮后，按 test 集分数（不是 train）取最高的那版作 best_description——这是 "selected by test score rather than train" 那行注释的实际含义。

run_eval.py 怎么真的测一个 description 会不会触发

这是整个流程最巧妙的一段，值得单独讲。run_single_query() 的流程：

  1. 临时建一个 command 文件：把待测 description 写成 <project-root>/.claude/commands/<skill-name>-skill-<8位随机后缀>.md， 里面 YAML frontmatter 就放这条 description。这样它就出现在 Claude Code 的 available_skills 列表里。
  2. 启一个独立 claude -p：用 subprocess.Popen 跑 claude -p <query> --output-format stream-json --include-partial-messages。 特意删掉 CLAUDECODE 环境变量，绕开"不允许嵌套"的检查。
  3. 读 stream event 检测触发：一旦看到 content_block_start 且 tool_use.name == "Skill"，再看 input_json_delta 里有没有那个 unique 名字—— 有就立刻返回 True，杀掉子进程；如果出现了别的 tool（说明 Claude 决定不用 skill），返回 False。
  4. 清理：不论成功失败，删掉那个临时 command 文件。

为什么要用 stream event 早判而不是等最终消息？因为如果等 skill 真的被加载然后跑完，每条 query 都要等 30 秒；而看 stream 在 skill 名字出现的那个 partial JSON 就能 ≤1 秒判定。20 条 query × 3 次 × 5 轮 = 300 次 claude -p，省这个等待是数量级差距。

improve_description.py 长什么样

就是把 (failed_triggers, false_triggers, history, 整个 SKILL.md body) 拼成一个 prompt，调一次 claude -p --output-format text 让它在 <new_description>...</new_description> 里返回新版。prompt 里有几条值得留意的策略：

  • "do NOT repeat these — try something structurally different" —— 鼓励模型换句式、换角度，不是局部微调
  • "generalize from the failures to broader categories of user intent" —— 不要列具体 query，要抽象到意图类别
  • 1024 字符硬上限。如果模型超了，就再 call 一次 claude -p，引用上一版的过长结果让它压缩

Step 4 · 应用结果

主 agent

run_loop 输出的 JSON 里有 best_description。主 agent 把它写回 SKILL.md frontmatter，给用户看 before/after 和分数对比。

7 · D · Ship 阶段

Bash · quick_validate.py

检查 SKILL.md frontmatter：name 必须 kebab-case、≤64 字符；description 必须存在、≤1024 字符、不能含 < 或 >；允许的顶级 key 只有 name / description / license / allowed-tools / metadata / compatibility 六个。

Bash · package_skill.py

先调 validate_skill() 卡一道，过了再把整个 skill 目录打成 zip，扩展名 .skill。打包时排除 __pycache__/ / node_modules/ / *.pyc / .DS_Store；根目录下的 evals/ 整个排除（测试用例不该跟着发布走），但嵌套更深的 evals/ 不排除——这条规则在 ROOT_EXCLUDE_DIRS 里。

8 · 这套评测的两条硬性局限

读到这里应该能意识到一件事：B 阶段所有"跑 skill"的动作都发生在 Task subagent 内部， 而 Task subagent 在 Claude Code 里有两条结构性约束。它们直接决定了哪些类型的 skill 用这套评测测不动。

局限 ① · 测不了"自己还要派 subagent"的 skill

executor 本身就是一个 Task subagent。而 Claude Code 的 Task 工具默认不允许嵌套—— subagent 里通常拿不到 Task 工具（具体取决于 subagent type 的 tool 白名单，但默认 Task 不在内）。

所以如果你正在写的 skill 是 orchestrator 类型——比如它的核心动作就是"派一组 worker subagent 并行处理 N 个文件"、 "派一个 reviewer subagent 评审 PR"——那么 executor 跑到那一步要么报错、要么 fallback 成自己 inline 做， 评测结果反映不出 skill 在真实场景下（用户在主 agent 里调用时，Task 是可用的）的表现。

局限 ② · 测不了多轮交互的 skill

executor 的 prompt 模板是固定的：

Execute this task:
- Skill path: ...
- Task: <eval prompt>
- Input files: ...
- Save outputs to: ...

一次性派发、一次性收回。中间没有任何机制让 executor 回头问用户问题。

很多 skill 的精髓恰恰在多轮交互：先访谈用户搞清楚意图、根据中间结果让用户做选择、出 plan 等用户确认、根据用户反驳调整方向…… 这些 skill 在 B 阶段只能被压成"单 prompt 输入 → 单产物输出"的退化形态来测。 退化版本的 pass rate 高，不代表真实使用体验好；反过来真实体验好的 skill 在退化测试里也可能拿不到分。

C 阶段的 description optimization 也共享这条局限——claude -p 本来就是 one-shot 非交互模式， 触发判定看的就是"用户单条 query 进来，会不会加载 skill"，多轮澄清后才显出价值的 skill 在 trigger eval 上同样吃亏。

什么 skill 适合这套评测

反过来说，这套评测最适合的形态非常窄：一次派发、自包含完成、产物可客观判分 的任务型 skill。例如：

  • 文件转换类（invoice → CSV、Markdown → docx、log → 结构化 JSON）
  • 固定 workflow 类（按模板生成报告、按规则改写代码）
  • 有确定性脚本可挂载的类（OCR、PDF 表单填写、图表绘制）

不太适合：

  • orchestrator / multi-agent 类（局限 ①）
  • 需要澄清式访谈或迭代调整的 advisory 类（局限 ②）
  • 主观风格类（虽然能跑，但 SKILL.md 自己也说这类"better evaluated qualitatively"，跑量化 benchmark 意义不大）

9 · 容易被忽略的工程决策

设计原因
B 阶段 executor 必须同 turn 派跨 turn 的 Task 会被串行化；2N 个 executor 一起后台跑 wall clock 才真的并行
assertions 在 executor 跑期间起草Step 1 派完任务，主 agent 有几分钟空闲；不利用就是浪费
timing 数据必须在 notification 到达时立刻写盘那条 notification 是唯一来源；过了就再也拿不到 token/duration
grading.json 字段名硬约束 text/passed/evidenceviewer 直接拿这三个 key 显示；主 agent 给 grader subagent 派任务时必须指定，不然 viewer 空白
C 阶段用 claude -p 而不是 Task subagent要模拟"陌生 Claude Code 会话第一次看见这个 skill"的判断；Task 共享父进程上下文，做不到
C 阶段必须传当前 session 的 model id不同 model 的触发偏好不同；用错 model 调出来的 description 上线就退化
improvement 模型看不到 test 分数（blinded_history）避免主动 overfit 到 test；test 只在最后选 best 时用
run_eval 用 stream event 早判触发每条 query 从 30s 压到 1s 内，300 次 query 才跑得动
临时 command 文件每次用新 unique 后缀20 worker 并发时避免名字冲突 + 防止前一次的残留干扰判断
analyzer benchmark 模式不能提改进建议角色分工：模式发现归 analyzer，改 skill 归主 agent 的 improvement 步骤

10 · 一句话总结每个角色

角色谁一句话
主 agent当前 Claude Code 会话读 SKILL.md 当剧本，访谈、draft、派 subagent、跑脚本、改进、循环
ExecutorTask subagent装作普通用户跑一次 eval prompt，留下 transcript 和产物
GraderTask subagent读一个 run 的 transcript+outputs，按 assertions 给 pass/fail 和 evidence
Analyzer（benchmark）Task subagent在跨 run 数据里捞模式，但不提改进建议
ComparatorTask subagent盲评 A/B 两份 output，按 rubric 选赢家
Analyzer（post-hoc）Task subagentunblind 后分析赢家为什么赢，输出有优先级的 improvement_suggestions
run_loop.pyBash Python 脚本组织 5 轮 "测当前 description → 让 LLM 改 → 再测"，按 test 分数选最优
claude -p worker独立 Claude Code 进程装作陌生会话，告诉脚本"这条 description 会不会让我加载这个 skill"
用户人确认 prompts、审 viewer、留 feedback、改 trigger query 集
