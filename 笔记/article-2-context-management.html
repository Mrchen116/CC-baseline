Claude Code 上下文管理拆解：朴素 agent loop 撑不到 30 轮，CC 在 LLM 调用前藏了 5 道关

讲 agent 设计的入门文章常常给出一个"agent loop"——其实就是十几行伪代码。看起来人人都能写一个。

但真去用它跑一个稍微长点的任务（比如让模型读 10 个文件、改 5 处代码、再写测试），你会发现这个朴素 loop 撑不到 30 轮就把上下文塞爆。模型会吐 prompt-too-long，或者更糟——勉强不报错，但 prompt cache 完全失效、每轮重写 30 万 token。

Claude Code 没有重写 agent loop 的形状，它在 每次 LLM 调用之前插了 5 道关，专门解决"上下文越用越胀"的问题。本文要做的就是：

  1. 先用伪代码把朴素 agent loop 写出来，看它的死法；
  2. 再看 CC 在朴素 loop 里偷偷加了哪 5 道关；
  3. 5 道关一个个展开——它们粒度从细到粗、代价从轻到重，每一道都为了让"轻量手段先解决问题，重型手段是最后兜底"。

一、最朴素的 agent loop，和它必死的方式

把"用工具的对话型 agent"剥到只剩主干，逻辑大概长这样：

const messages = []
const systemPrompt = "You are a helpful agent..."
const tools = [Read, Write, Bash, ...]

while (true) {
  // 1. 拿一条新输入
  const userInput = await getUserInput()
  messages.push({ role: 'user', content: userInput })

  // 2. 内层循环：让模型自由用工具，直到它不再 tool_use
  while (true) {
    const response = await llm.call({ systemPrompt, messages, tools })
    messages.push(response)

    if (response.toolCalls.length === 0) break

    // 3. 执行工具，把结果作为下一条 user 消息
    for (const tc of response.toolCalls) {
      const result = await executeTool(tc)
      messages.push({
        role: 'user',
        content: [{ type: 'tool_result', tool_use_id: tc.id, content: result }],
      })
    }
  }
}

这个 loop 没问题——逻辑是对的、能跑——但它有一个致命的不变量：messages 数组只增不减。每轮 LLM 调用都把 所有历史 重新发一遍。

为什么撑不到 30 轮

真实任务里 tool_result 是上下文增长的主力：

  • 读一个 1000 行的源文件 → 30K tokens
  • 跑一个 grep，命中 50 处 → 5K~10K tokens
  • 看一份 build 日志 → 20K~50K tokens
  • 查一个 npm 包文档 → 10K+ tokens

20~30 轮工具调用之后，messages 数组里堆了几十万 token——大部分是已经看过、不会再看的旧 tool_result。但朴素 loop 把它们一字不落地塞回去，于是：

  1. 硬上限：API 直接报 prompt-too-long，任务死掉；
  2. 软退化：还没炸但已经接近上限，每轮处理几十万 token，成本和延迟都明显恶化，更糟的是模型注意力涣散——重要的近期信息被淹没在大段陈旧 tool_result 里，回答质量肉眼可见地下降。
所以问题的本质不是"上下文太大"，而是"上下文里大部分是无用的历史"。解药不是无限扩窗（贵且慢），而是有针对性地砍掉确定无用的部分。

但"砍"也不能乱砍——prompt cache 的硬约束

设计任何上下文压缩方案，都要随时记住一个事实：Anthropic 的 prompt cache 是 prefix hash 命中。从 messages 开头到某个位置的内容只要有一个字节变化，从那个位置往前的整段缓存就全部作废，下一轮要重新写入 cache（写入价是读取价的几倍）。

这给"砍历史"带来一个反直觉的约束：

  • 砍末尾几乎免费——前缀仍然命中。
  • 砍中段或前段则灾难——前缀变了，从砍点往后到末尾的所有缓存全部失效。
  • 就算只是把"已发过的旧 tool_result"原地改成"占位符"，同样会破坏 cache。

这个约束直接塑造了 CC 这 5 道关的形态——你会在后面反复看到这些设计动作：

  • 第 1 道把 tool_result 划成 mustReapply / frozen / fresh 三类，frozen 永远不许动，就是怕动了破坏 prefix；
  • 第 3 道的"热路径"干脆不改本地 messages，而是发 cache_edits 让服务端在缓存层删，绕过 prefix 改写；
  • 第 4 道用 projectView() 投影代替插入新消息，避免动 messages 数组；
  • 第 5 道"完整 compact"会彻底改写历史——这就是为什么它是最后的兜底，因为它必然废掉整段 cache。

读完这一节，你已经能理解 5 道关排序的另一层动机：能保 cache 就保 cache，必须破坏 cache 的方案放最后。

二、CC 的解法：在 LLM 调用前藏了 5 道关

把 CC 的 query.ts 内层循环拍扁成伪代码，跟朴素版逐行对比：

while (true) {
  // ↓↓↓ 朴素 loop 这里直接 llm.call(messages)
  // ↓↓↓ CC 在这之前藏了 5 道关 ↓↓↓
  let messagesForAPI = messages
  messagesForAPI = applyToolResultBudget(messagesForAPI)        // ① 工具结果预算
  messagesForAPI = snipCompactIfNeeded(messagesForAPI)          // ② 段落删除
  messagesForAPI = await microcompactMessages(messagesForAPI)   // ③ 旧 tool_result 清理
  messagesForAPI = await contextCollapseIfNeeded(messagesForAPI)// ④ 分段归档
  messagesForAPI = await autocompactIfNeeded(messagesForAPI)    // ⑤ 重型兜底
  // ↑↑↑ 5 道关之后才发给 LLM ↑↑↑

  const response = await llm.call({ systemPrompt, messages: messagesForAPI, tools })
  messages.push(response)

  if (response.toolCalls.length === 0) break
  for (const tc of response.toolCalls) { /* 同上 */ }
}

注意一个关键事实：5 道关都只改 messagesForAPI，不改 messages 本身。messages（更准确说是写进 JSONL 的事件流）是持久真相，永远不动；messagesForAPI 是本轮发给 LLM 的视图，随便剪。这与上一篇《session 存储拆解》里"harness 工作内存 vs 持久档案"的边界一致。

图 1：5 道关排成漏斗，前 4 道是轻量手段（不调 LLM 或只调小模型），第 5 道是重型兜底。每一道都只动 messagesForAPI，不动 messages 本身。

把 5 道关并排放进一张表，作为后续展开的索引：

步名字粒度调 LLM？公开 build 里能看到解决什么问题
①applyToolResultBudget单条 tool_result否完整实现单轮工具返回太大，把当前消息直接撑爆
②snipCompactIfNeeded历史区段否（模型决策）仅接口签名 build 剥离显然无用的旧历史段（debug 完成、结论得出）
③microcompactMessages旧 tool_result否冷路径完整 / 热路径仅签名累积的旧工具结果占大头
④contextCollapse多个消息区段后台小模型仅接口签名 build 剥离接近上下文上限，需要分段归档保留细粒度
⑤autocompact整段历史是（完整 compact 分支）完整实现前 4 道都没救住的重型兜底
读完这张表已经能理解 80% 的设计：5 道关按"代价从轻到重"排列，前面能省事就不到后面。第 1、3 步连模型都不用调，靠规则和缓存就把大头砍了；第 2、4 步引入小模型做精细决策；只有第 5 步的"完整 compact"分支才会调主模型重写整段历史——而且会丢失原始消息粒度，所以是兜底中的兜底。

三、第 1 道：applyToolResultBudget — 工具结果预算

解决的问题：单轮里若干并行 tool_use 同时返回，几条加起来就能撑爆当前 user message。这不是历史累积问题，是单轮就能炸的急性问题。

3.1 预算上限按"模型实际看到的 wire 体积"算

默认上限：每条 API-level user message 内所有 tool_result 加起来 ≤ 200K 字符（MAX_TOOL_RESULTS_PER_MESSAGE_CHARS，可由 GrowthBook flag tengu_hawthorn_window 覆盖）。

注意"API-level user message"这个限定：本地状态里 N 条分散的 user 消息，经 normalizeMessagesForAPI 合并连续 user 后，在模型眼里可能只是一条。预算必须按合并后的体积算，否则 N 条各自"看似不超预算"的结果合并后会直接突破上限。

3.2 三类 tool_result：mustReapply / frozen / fresh

组内的 tool_result 被分成三类——这是这一道关最讲究的地方：

图 2：三类划分的设计动机是 prompt cache 前缀稳定。mustReapply 用同一份字符串，frozen 不许动，只有 fresh 可以挑大的替换。

3.3 一个具体例子

一条 API user message 里有 5 个并行 tool_result，大小分别是 80K、80K、80K、10K、10K，总 260K：

  • frozenSize = 0，freshSize = 260K，limit = 200K → 超预算。
  • fresh 排序后：80K、80K、80K、10K、10K。
  • 替换第一个 80K：remaining = 180K ≤ 200K，停止。
  • 实际只替换 1 个 80K 的结果；其余 4 个保留原样。

另一个例子：5 个结果都是 60K，总 300K——替换第一个后 240K（仍超），替换第二个后 180K（停止）。最终替换 2 个。

3.4 替换后长什么样 + 为什么要写入磁盘

被选中的 tool_result 由 persistToolResult 写入磁盘（文件名按 tool_use_id 命名，已有则跳过），原内容替换成：

<persisted-output>
Output too large (...). Full output saved to: /path/to/persisted/tu-006.txt
Preview (first 2000 bytes):
... 前 2000 字节预览 ...
</persisted-output>

这里有一个非常关键的设计：替换状态按 tool_use_id 持久化记忆。一旦某个 tool_result 被替换过，下次它再出现在 messages 里（同一个 session 后续轮次），就走 mustReapply 路径，用完全相同的 replacement 字符串。这意味着——

同一个 tool_result 在它出现的所有后续轮次里，要么都是原文、要么都是同一份替换。绝不会"这一轮替换、下一轮又变回去"或"两轮替换内容不同"。这是为了让 prompt cache 的 prefix hash 在跨轮次之间保持稳定——cache 是 prefix 命中，一字之差全废。

四、第 2 道：snipCompactIfNeeded — 段落删除 公开 build 仅签名

解决的问题：有些旧历史段对当前任务显然无用了——比如用户排查 bug 已经得出结论、或者一段探索分支已经被放弃。autocompact 会把它们一并丢进总结，但其实直接删掉更好（不耗总结成本、保留细粒度）。

提醒：这个模块在公开 build 里只剩接口签名（// Auto-generated stub），不能从公开仓库直接跑出 snip 行为。但接口、调用点、resume 恢复逻辑、context_efficiency 附件里的注释（讲 nudge 节奏）、消息上的 [id:xxxxxx] 短 ID 标签等多重线索拼起来，设计意图非常清楚——下面讲的就是从这些线索逆推出的最可能算法。

4.1 触发节奏：nudge 模型，不是硬阈值

不是"超过 X token 立即 snip"，而是给模型发提示（nudge）。shouldNudgeForSnips 用 10K token 的间隔节奏触发提示——但提示之后仍要由模型决定该不该 snip、snip 哪段。

这个间隔在 之前的提示、已有的 snip 标记、snip 边界、compact 边界之后都会重置。整体是"上下文变重时鼓励模型做这件事"，而不是机器自动执行。

4.2 两阶段执行：标记（marker）→ 边界（boundary）

  • 标记：内部登记标记，由 SnipTool 或 /force-snip 入口写入"哪段历史可裁剪"。
  • 边界：在每轮 query 前，snipCompactIfNeeded() 把标记真正落地——删掉中段消息、记录 removedUuids、修复幸存消息的 parentUuid 链。

4.3 SnipTool 的输入形态

当 HISTORY_SNIP 真正运行时，系统会给发往模型的 user message 末尾追加 [id:xxxxxx] 短 ID 标签（注释明确写"for snip tool referencing"）。从这个线索倒推，SnipTool 最可能的输入：

{
  spans: [
    {
      start_id: "a1b2c3",   // 区段起点（某条 user message 末尾的短 ID）
      end_id:   "d4e5f6",   // 区段终点（另一条 user message 末尾的短 ID）
      reason:   "这段排查已得出结论，后续不需要保留完整原始过程"
    }
  ]
}

注意 start_id / end_id 都对应 user message 的短 ID——意思是"从某个用户回合开始，到另一个用户回合结束"，中间夹着的 assistant / tool_use / tool_result 一起算进 snip 区间。

4.4 删除的视图策略：API 砍、UI 留

执行后并不一定把原始消息从界面层抹掉：

  • REPL：保留全量 transcript，方便用户向上滚动查看历史；
  • API 视图：通过 projectSnippedView() 投影掉被 snip 的消息，模型看不到；
  • JSONL：原始消息物理保留，removedUuids 写到 snip boundary 元数据；resume 时按记录重放删除（这与上一篇里"compact 不删 JSONL"的原则一致）。

函数返回 tokensFreed，给后面的 autocompact 做阈值修正——避免 autocompact 拿着 stale usage 误判触发。

五、第 3 道：microcompactMessages — 旧 tool_result 清理

解决的问题：哪怕没炸单轮预算、也没显然该删的段，长会话里仍然累积了大量旧 tool_result。微压缩专门处理这部分。

5.1 只动 COMPACTABLE_TOOLS 内的工具

不是所有 tool_result 都被压。COMPACTABLE_TOOLS 是一个白名单，里面是适合压缩的工具（典型如 Bash 输出、grep 结果）；像 Read 这种用户可能反复回看的工具结果不在白名单里，永远保留原文。

5.2 冷路径：60 分钟 idle 后清空

判定条件：距离上一条 assistant 消息超过 60 分钟。这时认为服务端 cache 基本过期了，怎么改都不亏。直接把较老的 tool_result 内容清空成：

[Old tool result content cleared]

只保留最近 5 条。这条路径完整实现、生效中。

5.3 热路径：cache_edits 服务端删除 公开 build 仅签名

当 cache 还热（距上次 assistant 不久）+ 模型支持 cache editing + 主线程（非子 agent）时，走另一条路：不动本地 messages，而是给请求附加 cache_edits 指令，让服务端在缓存前缀里直接删掉旧 tool_result。

这条路径的好处是本地 messages 完全不动、prompt cache 命中保住——你删的不是"要发的内容"，是"已缓存前缀里的部分"。

触发条件是计数：每轮 query 前扫描完整对话历史，把还没登记过的 compactable tool_result 注册进 cachedMCState（toolOrder 记录顺序、deletedRefs 记录已删的）。当——

活跃数 = toolOrder.length - deletedRefs.size
活跃数 > triggerThreshold ?
  ├─ 是：生成 cache_edits，从最老的批量删，保留最近 keepRecent 条
  └─ 否：什么都不做

triggerThreshold 和 keepRecent 来自 GrowthBook 远程配置。系统提示语会提前告知模型"The N most recent results are always kept"，让模型对"老结果可能消失"有心理准备。

5.4 冷热双路径的设计直觉

冷路径热路径
判定idle > 60mincache 热 + 支持 edits + 主线程
动作本地 messages 改成占位符本地不动，发 cache_edits 给服务端
cache 影响反正过期了，不在乎必须保住命中
公开 build完整实现仅签名（剥离）

一句话理解：cache 已废就直接改本地、cache 还热就让服务端帮删。两条路径目标都是"砍掉旧 tool_result"，但优化的对象不一样。

六、第 4 道：contextCollapse — 分段归档 公开 build 仅签名

解决的问题：接近上下文上限时，autocompact 会粗暴地把整段历史压成一个总摘要——粒度太粗。Context Collapse 想做的是"按多个 span 分段归档"，让最近上下文继续保持原始消息粒度。

6.1 触发线：90% commit-start / 95% blocking-spawn

注释里明确写到：collapse 模式下由 90% 启动后台 commit、95% 阻塞式生成来管理 headroom。一旦 isContextCollapseEnabled() 为真，会抑制主动式 autocompact——意思是"collapse 接管，autocompact 别抢"。

6.2 lifecycle：staged → committed

类型定义里有两套状态：

  • stagedSpans：已识别为可折叠的消息区段，但尚未生成摘要。{ startUuid, endUuid, summary, risk, stagedAt }
  • collapsedSpans / collapsedMessages：已经由后台代理（ctx-agent）总结、提交的折叠记录

设计上是异步两阶段：

  1. 主线程发现"这段历史可以折叠"，扔进 stagedSpans 排队，不阻塞当前 query
  2. 后台启动 ctx-agent 拉总结，成功后提交为 collapsed span

6.3 读取时是投影不是插消息

这是 collapse 和 autocompact 最大的区别。autocompact 是把摘要消息插进 messages 链；collapse 不动 messages 链，读取时通过 projectView() 投影——把 firstArchivedUuid..lastArchivedUuid 区段在视图里替换成 <collapsed id="...">summary</collapsed> 占位符。

这种"投影式"压缩的好处：跨 turn 持续生效，且不打破 messages 数组本身的结构。ContextCollapseCommitEntry 持久化的也只是"摘要占位符 + 拼接指令"，原始消息已在 transcript 里，不重复存。

6.4 强制排空（drain）：413 错误时的兜底

错误恢复链里，prompt-too-long 不立即触发响应式压缩，而是先走 recoverFromOverflow()——把所有 staged 的 collapse 区段强制排空（赶紧总结、立刻 collapse），用新视图重试。只有这条路也失败，才退化到 reactive autocompact。

设计目标是保留细粒度上下文，避免退化成整段摘要。把 collapse 想成 "soft compact"——按段折叠，最近上下文留原文；只有 collapse 也救不了的时候，才让 autocompact 出手做"hard compact"。

七、第 5 道：autocompact — 重型兜底

解决的问题：前 4 道关都没把上下文压到阈值下。autocompact 用当前 messagesForQuery 估算 token，减去 snip 释放的 tokensFreed，仍然超阈值就触发。

autocompact 自己分两条分支——能不调 LLM 就不调：

图 3：autocompact 优先走 session-memory（免费的、靠后台维护好的总结文件）；失败才走完整 compact（调 LLM 现场重写一段总结）。

7.1 分支 A：session-memory compact（不调 LLM）

关键洞察：session-memory 文件不是 compact 时现场生成的，而是会话过程中由 post-sampling hook 在后台持续维护的一份 markdown 记忆文件。compact 触发时直接读这份文件即可，不需要重跑 LLM。

compact 后真正发给 LLM 的 messages 大致是：

0. user (isMeta=true)         // userContext reminder
   <system-reminder>CLAUDE.md + currentDate</system-reminder>

1. user (isCompactSummary=true)
   "This session is being continued from a previous conversation that ran out
   of context. The summary below covers the earlier portion of the conversation.

   # Current State
   - 用户当前在看 query.ts 的上下文压缩链路
   - 已确认 applyToolResultBudget / microcompact / autocompact 的职责

   # Important Findings
   ...

   # Next Step
   - 继续理解完整 compact 的 prompt 和产物

   If you need specific details from before compaction, read the full transcript at:
   /path/to/session.jsonl

   Recent messages are preserved verbatim."

2-N. assistant/user/...        // messagesToKeep 中的原始消息（一段最近尾巴）
N+1. user (isMeta=true)        // 由 attachments / hookResults 归一化而来

"最近尾巴"不是固定几条消息，而是一段足以继续工作的尾部上下文：默认要求 ≥10K tokens、≥5 条带文本的消息，尽量控制在 40K tokens 内，且不能拆开 tool_use/tool_result 配对。

7.2 分支 B：完整 compact（调 LLM）

session-memory 不可用、为空、或压完仍超阈值时，回退到 compactConversation()。这条路径会把整段历史发给 总结模型（不是主对话模型），加一个特定 prompt——

[messages parameter]
0. user/assistant/...       // 原来的整段历史消息

N. user message             // summaryRequest（追加在末尾）
   content: NO_TOOLS_PREAMBLE
          + BASE_COMPACT_PROMPT
          + optional customInstructions
          + NO_TOOLS_TRAILER

"禁止调用工具、只能返回纯文本总结"是这条 user message 文本的一部分，不是单独消息。

模型返回一份 9 段结构化总结：

Summary:
1. Primary Request and Intent:        ← 用户在做什么、目标是什么
2. Key Technical Concepts:            ← 涉及的关键技术词
3. Files and Code Sections:           ← 看过/改过的文件清单
4. Errors and fixes:                  ← 期间踩过的坑和解法
5. Problem Solving:                   ← 整体推理路径
6. All user messages:                 ← 用户提过的所有指令
7. Pending Tasks:                     ← 待办
8. Current Work:                      ← 当前在做什么
9. Optional Next Step:                ← 下一步建议

这 9 段不是随手列的——它对应 agent 任务里"要继续往下走必须知道的所有事"。代码从模型回复里提取 summary 文本（剥掉 <analysis> 包装），用 getCompactUserSummaryMessage() 包成 compact summary message。

7.3 完整 compact 后的 messages 结构

0. user (isMeta=true)         // userContext reminder

1. user (isCompactSummary=true)
   content: "...Summary: 1. Primary Request... 2. Key Technical Concepts... ..."

2. user(s) (isMeta=true)      // attachments：最近读过的文件（最多 5 个）
                              // + plan file / invoked skills / MCP instructions / agent status

3. user(s) (isMeta=true)      // hookResults：SessionStart hook additional context

注意几个细节：

  • 没有"原始尾巴"——这是和 session-memory compact 最大的区别。原始历史整段被 compact summary 替代，模型只能看到摘要 + 通过 attachments 补回的少量运行态上下文。
  • "最近读过的文件内容"会被重新读一次：默认最多 5 个，受单文件和总 token budget 限制。这是为了让模型在压缩后还能"摸到"代码当下的状态。
  • invoked skills 只在完整 compact 路径补，session-memory 路径不补。

7.4 为什么有两条分支

这是整篇文章的一个点睛：同一道关里再分"轻"和"重"。

session-memory完整 compact
调 LLM？否（读文件）是（现场总结）
原始尾巴保留 ≥10K tokens / ≥5 条没有，整段被替代
触发场景SessionMemory 文件已就绪session-memory 不可用 / 失败
代价~0（一次磁盘读）跑一次完整总结请求

能用文件就用文件，是因为SessionMemory 在会话期间已经由后台 hook 在维护——这份维护本来就要做（用于其他场景），compact 只是顺手用一下。这是典型的"已有的工作要榨干"思维。

八、5 道关串起来的设计哲学

把 5 道关重新排一遍，会发现它们沿三条轴递进：

轴① ToolResultBudget② Snip③ Microcompact④ Collapse⑤ Autocompact
粒度单条 tool_result历史区段旧 tool_result多个 span整段历史
动作替换为占位字符串删除清空 / 服务端删分段总结+投影整段总结
调 LLM否否（模型决策）否后台小模型是（完整分支）
是否丢失原始否（写盘可恢复）否（JSONL 保留）否（占位符）否（投影）是

三条规律一目了然：

  1. 越靠后代价越高：从规则替换 → 模型决策 → 后台小模型 → 主模型重写。前 4 道都不调主模型。
  2. 越靠前粒度越细：单条 → 区段 → 类型 → 多 span → 整段。粗粒度只在前面无效时才用。
  3. 只有第 5 道"完整 compact"会丢失原始消息粒度。前 4 道都做到了"压而不毁"——要么替换可还原（写盘）、要么删除有记录（removedUuids）、要么投影不动数据（projectView）、要么占位符可展开（<collapsed>）。

这三条规律一起构成 CC 上下文管理的核心设计：

能不调 LLM 就不调，能保留原文就保留，能用前一道关解决就不到后一道关。5 道关像漏斗一样把不同性质的"上下文膨胀"分流处理——单轮急性问题在第 1 道就死掉、累积型旧 tool_result 在第 3 道处理掉、显然无用的旧段在第 2 道删掉、即将超阈时在第 4 道分段归档保细粒度——只有这些都失败时，第 5 道的"完整 compact"才会出手做"丢精度换 token"的硬交易。

关于"公开 build 仅签名"的那 3 道关，最后澄清一句：snip、cachedMicrocompact 的热路径、contextCollapse 三个模块在公开构建里都只剩 // Auto-generated stub 这种占位实现——但这并不代表 Anthropic 内部没实现。从这套接口、调用顺序、状态字段、错误恢复链路、context_efficiency 附件里的注释、还有恢复逻辑里对 removedUuids / collapsedSpans 的处理来看，这些功能内部跑得完整且体系化，只是公开 build 在打包时把它们剥离了（具体原因可能是内部 feature flag、依赖内部基础设施、或还在灰度）。所以本文里出现"仅签名"标签的地方，讨论的是从接口/恢复路径反推出来的设计意图，而不是"未实现的功能"。

反过来说，从公开 build 能看到这套接口骨架本身就是一个有用的事实：5 道关之间的边界、调用顺序、状态字段都被钉死了——这意味着 Anthropic 内部即便频繁调整每一道关的实现策略（比如换 collapse 触发线、换 snip 决策模型），整个链路结构也是稳定的。这与上一篇session 存储拆解里"harness 一直在变、session 不变"的命题在同一条轴上：变化被关在叶子节点的实现里，骨架往外暴露的是稳定接口。
