Claude Code cache_edits 拆解：一种不破 cache、不重算 KV 的上下文压缩

Agent loop 跑久了都会撞同一个问题：上下文越拉越长，每多一个旧 tool_result 都在持续吃 attention 成本（attention 复杂度 O(N) per token），而且最终会撞到 context 上限。Claude Code 仓库里围着这个问题堆了一摞压缩手段：snipCompactIfNeeded、autocompact、contextCollapse、microcompactMessages……

其中专门治理"旧 tool_result 太占上下文"的是 microcompactMessages。它有冷热两条路径：

  • 冷路径：距上次 assistant 消息超过 60 分钟、cache 已经凉。这时候直接把较老的 tool_result 的 content 字段就地置成 [Old tool result content cleared] 占位符，只保留最近 5 条。这条路径粗暴但简单——反正 cache 都凉了，重算就重算。
  • 热路径：cache 还热的时候要干完全相同的事——把旧 tool_result 从模型有效上下文里拿走——但不愿意付冷路径那两笔代价（破 prefix hash、被删内容彻底消失）。这条热路径的实现就是本文要拆的 cache_edits。

cache_edits 想拿到的事情其实挺尖锐：在 cache 还热的场景里压缩上下文，同时既不破 prompt cache 的 prefix hash、也不让被删除的内容彻底从模型那里消失。这两件事普通压缩方案二选一已经不容易，cache_edits 试图两个都要。它怎么做到的，就是这篇文章要展开的内容。

本文是一篇推测分析，不是权威说明。cache_edits 不在 Anthropic 公开文档里。我们能看到的是：(1) Claude Code 反编译代码里完整的客户端骨架；(2) 代码里一段提到内部服务栈 "Mycro / page_manager" 的注释；(3) 一些 Reddit 逆向帖和社区分析。从这些线索能拼出"最可能的实现形态"，但没法确认细节——尤其是服务端那一层（§4 §5）很大程度上是合理外推。文章里每段都会标 代码已证实 或 合理推测，请按这个标签对待。如果你了解更多事实、或对推测有不同看法，非常欢迎在评论区指正。

本文要做的：

  1. 先把冷路径要付的两笔代价讲清（§1）——这是 cache_edits 存在动机的全部；
  2. 从代码里钉死客户端骨架和生命周期（§2 §3）；
  3. 顺着代码注释拼出服务端最可能的实现（§4）；
  4. 讲清核心机制：为什么 cache_edits 既能不重算 KV，又能让被删除的部分通过 C 的 K/V 隐式留下影响（§5）；
  5. 最后讨论这套机制为什么只能是 first-party，以及如果它真按推测的方式工作，对 Anthropic 意味着什么（§6 §7）。

一、冷路径在做同一件事，但代价限制了它只能在 cache 凉时启用

先看冷路径具体怎么干。microcompactMessages 冷路径的核心动作很直接：把较老的 tool_result 的 content 字段就地置成 [Old tool result content cleared]，结构（block 类型、tool_use_id 等）保留，最近 5 条不动。这个改动直接作用在 messages 数组本身——下一次请求发出去的 messages 里，那些 tool_result 的 content 真就是占位符了。

这个简单动作干完之后会付两笔代价：

代价 1：prefix hash 从第一处改动起破了。Anthropic 官方 prompt cache 是 prefix hash 命中——从 messages 头部到 cache breakpoint 整段做哈希，前缀只要变一个字节，从那点之后整段缓存全废。"清空 content" 也是改字节，cache miss 不可避免。服务端要把后面所有内容重新跑一遍 prefill 算 KV——在 100K+ 的长 session 上，这一次重算的开销远超被压掉那几个 tool_result 节省的 attention 成本。

代价 2：被压缩部分的"影响"也跟着消失了。这一点比代价 1 更关键，但容易被忽略。模型重新 prefill 的时候，看到的 messages 是 A · [placeholder] · C 的纯文本——服务端会重新算每个 token 的 K/V。重算 C 的 K/V 用的是 "C 看不见 B" 的语境（C 前面的 content 已经是 placeholder 了），原本 C 的 K/V 里凝固着的"我看过 B 时形成的判断"全部丢失。从模型角度，B 不只是从 attention 范围里消失了，连 B 当时对 C 的影响痕迹都被抹掉。这一点为什么重要、cache_edits 怎么避开它，§5 会展开讲。

这两笔账一加起来，冷路径的触发条件就很明确：必须等 cache 已经凉了（距上次响应 > 60 分钟）才启用。反正 cache 都凉了，代价 1 不可避免，索性把 messages 也清理一下；代价 2 在长间隔后也没那么要紧（用户可能换了任务）。冷路径是"反正都要付代价了，索性清干净"的兜底方案。

但 cache 还热的场景下旧 tool_result 同样在堆积——长 session 经常在几分钟内连续工作，cache 一直热着，旧 tool_result 又确实在持续吃上下文。这时候按冷路径的方式去清就太亏了：为了压几个 tool_result 把整段 KV cache 都打掉。cache_edits 就是为这个场景设计的——同样要把旧 tool_result 从模型有效上下文里拿走，但既不改 messages（不破 prefix hash）、也不让 C 失去被 B 影响过的痕迹（不重算 KV）。

下面这张图先在 messages / cache 字节层面对比两条路径，§5 再回到 KV 内部讲清"为什么 C 不会失去 B 的影响"。

图 1：冷路径 vs cache_edits 在 messages 字节和 cache 命中状态上的对比。冷路径改的是请求体（即便只是把内容置空），prefix 从第一处变动起就破；cache_edits 不改请求体一个字节，只附一份"删除清单"让服务端按 cache_reference 释放对应 KV。

用一句话总结这层差别：冷路径改的是"客户端要发的内容"；cache_edits 改的是"服务端 cache 的有效视图"。

客户端原始消息里 A · B · C 三段一字不少都在（包括 B 内所有 reasoning、text、tool_use、tool_result），cache prefix hash 仍然命中——只是 B 内被标了 cache_reference 的 tool_result 在服务端被打了"释放标记"，对应的 KV page 被回收，模型后续 attention 不再读它们。所以"删 B"是简化说法，准确表述是"只删 B 内的 tool_result"——下文涉及 KV / page 的讨论也按这个口径。

这就是 cache_edits 在请求层面的核心动作：把"想压缩的内容"和"要发的请求体"解耦——客户端继续发完整 prefix（cache 命中），同时附一份精确到具体 tool_result 引用的"删除指令清单"。但请求层面的差别只是表象——为什么这样做能避开冷路径"代价 2（C 失去 B 的影响）"，要看到 KV cache 内部才能讲清，§5 展开。

二、骨架：从代码里钉死的事实 代码已证实

看 cache_edits 怎么做到 §1 末尾承诺的那两件事——不改 messages、不重算 KV。下面这些不是推测，是 src/services/api/claude.ts 和 src/services/compact/microCompact.ts 里能直接读到的形状：

2.1 客户端会给 tool_result 补 cache_reference 字段

在 addCacheBreakpoints() 里，对所有位于最后一个 cache_control marker 之前的 tool_result，会补一个 cache_reference 字段，值就是 tool_use_id：

// claude.ts · addCacheBreakpoints
if (block && isToolResultBlock(block)) {
  msg.content[j] = Object.assign({}, block, {
    cache_reference: block.tool_use_id,
  })
}

关键事实：这是无条件给整个 cached prefix 里所有 tool_result 都加，不是只给"想删的"加。这意味着客户端事先不知道哪些会被删，先给所有可能被引用的 block 标好"引用键"，等触发时再决定删哪些。

2.2 cache_edits block 的精确形状

同一文件里能找到类型定义：

// claude.ts
type CachedMCEditsBlock = {
  type: 'cache_edits'
  edits: { type: 'delete'; cache_reference: string }[]
}

这是一个新的 content block 类型——和 text、tool_use、tool_result 平级——里面装一组 {type: 'delete', cache_reference: ...} 删除指令。

2.3 cache_edits block 插在哪里

insertBlockAfterToolResults 这个名字已经把规则写明：插入到最后一条 user message 的 content array 里、tool_result 块之后。所以请求体长这样：

messages: [
  { role: 'user',      content: [{ type: 'text', text: '初始任务...' }] },
  { role: 'assistant', content: [{ type: 'tool_use', id: 'tu-001', ... }] },
  { role: 'user',      content: [
      { type: 'tool_result', tool_use_id: 'tu-001', cache_reference: 'tu-001', content: '...' }
  ]},
  // ... 中间 30 轮 ...
  { role: 'user',      content: [
      { type: 'tool_result', tool_use_id: 'tu-040', cache_reference: 'tu-040', content: '...' },
      // ↓↓↓ 删除指令插在这里 ↓↓↓
      { type: 'cache_edits', edits: [
          { type: 'delete', cache_reference: 'tu-001' },
          { type: 'delete', cache_reference: 'tu-005' },
          { type: 'delete', cache_reference: 'tu-012' }
      ]}
  ]},
]

2.4 触发条件：count-based threshold

cachedMicrocompact.ts 里的状态机：

type CachedMCState = {
  registeredTools: Set<string>     // 已登记的 tool_use_id
  toolOrder: string[]               // 出现顺序
  deletedRefs: Set<string>          // 已删除的引用
  pinnedEdits: PinnedCacheEdits[]   // 已 pin 的 cache_edits 块
  toolsSentToAPI: boolean
}

每轮 query 前扫描 messages、注册新 tool_result。当：

活跃数 = toolOrder.length - deletedRefs.size
活跃数 > triggerThreshold ?

满足时，调 getToolResultsToDelete(state) 选出最老的一批，调 createCacheEditsBlock(state, toolIds) 生成 cache_edits block。triggerThreshold 和 keepRecent 都来自 GrowthBook 远程配置——这意味着 Anthropic 可以线上调参而不发版。

2.5 pin / consume 模式：删除指令要在每轮重发

这是最反直觉、也最关键的一点。microCompact.ts 暴露三个 API：

// microCompact.ts
export function consumePendingCacheEdits(): CacheEditsBlock | null
export function getPinnedCacheEdits(): PinnedCacheEdits[]
export function pinCacheEdits(userMessageIndex: number, block: CacheEditsBlock): void

流程：

  1. 本轮 microcompact 决定要删 [tu-001, tu-005, tu-012] → 生成新 cache_edits block 放进 pendingCacheEdits
  2. 下一次 API 请求构造时，consumePendingCacheEdits() 取出（且清空 pending）+ getPinnedCacheEdits() 取所有以前 pin 过的
  3. 新的 + 所有以前 pin 过的 都插入到对应位置的 user message 里
  4. 新的这一批 pinCacheEdits() 注册到 state，之后每一轮都要在同一位置重发

为什么要重发？因为客户端发的是完整 prefix（A B C），不重发删除指令的话，服务端没办法知道还要删 B——服务端的"已删除"状态不是持久存的，而是每次请求里由客户端的 cache_edits 列表声明出来的。换句话说：

cache_edits 是 declarative 的"本次请求里希望生效的删除集合"，不是 imperative 的"执行一次删除操作"。每次请求都要把所有想生效的删除全列出来。这也意味着 pin 列表是单调增长的——除非显式把某些删除"撤回"。

2.6 真实响应字段：cache_deleted_input_tokens

API 响应的 usage 对象里多了一个字段，sdkUtilityTypes.ts:22 和 claude.ts 里多处使用：

cache_deleted_input_tokens?: number

这是服务端告诉客户端"这次请求实际删除了多少 token"——可以用来做账、可以用来更新 token 预算。microCompact.ts 还会捕一个 baselineCacheDeletedTokens，记录上一次响应里的累计值，用差值算本次操作的实际收益。

三、完整生命周期 代码已证实

图 2：cache_edits 的完整生命周期。客户端做 4 件事（标注 / 触发 / 注入 + pin / 接响应），服务端做的事在最后一节展开。

这里有一个隐含但很重要的不变量——已经 pin 过的 cache_edits 必须每次 request 在同一位置重发。addCacheBreakpoints 里这段处理：

// 重新插入所有先前 pin 过的 cache_edits 到原来的位置
for (const pinned of pinnedEdits ?? []) {
  const msg = result[pinned.userMessageIndex]
  if (msg && msg.role === 'user') {
    insertBlockAfterToolResults(msg.content, dedupedBlock)
  }
}

userMessageIndex 是相对 messages 数组的位置——意味着客户端要保证 messages 数组的索引在多次 request 之间不能错位。这又是另一条"prefix 稳定"的硬约束：你不能在前面塞新消息，否则 pin 索引就错了。

四、服务端实现：cache_edits 是已有 eviction 机制的反向入口 来自代码注释

前面三节讲清了客户端怎么标 cache_reference、怎么发 cache_edits。但客户端不改 messages 字节，"让模型看不到 B"这件事必然发生在服务端。这一节回答：服务端到底拿 cache_edits 的删除清单做了什么。

claude.ts 里 addCacheBreakpoints 函数有一段注释，原本讲的是"为什么只用一个 cache_control marker"，但顺带泄露了服务端机制：

// Exactly one message-level cache_control marker per request. Mycro's
// turn-to-turn eviction (page_manager/index.rs: Index::insert) frees
// local-attention KV pages at any cached prefix position NOT in
// cache_store_int_token_boundaries. ...

读出来一个核心机制：Anthropic 服务端的 KV 缓存是按 page 管理的，每轮请求结束默认跑一次 eviction sweep——所有"位置不在 boundary 集合内"的 page 直接释放。cache_control marker 的作用是往 boundary 集合里加一个保护点，让对应 page 逃过这一轮的 evict。这里有个反直觉的点值得点出：

  • 常态是清，不是留——服务端默认每轮 evict 一切没受保护的 page，cache 能跨轮命中是因为 boundary 在保护它们。这和"prompt cache 默认会留内容、特殊操作才删"的直觉是反过来的。
  • cache_control marker 是"保护标记"，不是"插入标记"——它告诉服务端"别 evict 这个位置的 page"，不是"把这个内容缓存起来"。

有了这个心智模型，cache_edits 在服务端的角色就清楚了：

cache_edits 不是新协议，而是给已有的 page eviction 机制加了一个反向触发入口。原本只有一条触发路径——按 token 位置自动 evict（每轮跑、看 boundary）；cache_edits 加了第二条——按 cache_reference 主动 evict（客户端显式声明哪些 page 要释放）。底层调的还是同一个 page release 函数，page_manager 不变，attention kernel 不变；新增的工程量只是"cache_reference → page 集合"的索引 + 一个新的删除入口。

这一点对 §5 关键：cache_edits 在服务端"几乎不做什么"——既不动 attention 计算，也不重算任何 K/V，只是标记几个 page 为可释放。所以"压缩同时不重算 KV"这件事在工程上不是什么了不起的优化，而是 page_manager 这套已有架构上一个小小扩展自然带来的副产物。

五、核心机制：压缩同时不重算 KV，且 B 仍隐式留在 C 里 合理推测

到这里 §1 提的两个问题——"为什么 cache_edits 不破 prefix hash"、"为什么被删除的 B 不会让 C 失去影响"——前者已经讲清（不改 messages 字节、服务端 page 释放走另一条入口）；后者要看到 KV cache 内部才能讲清，这一节就讲这个。

本节先把问题做一次模型层面的抽象简化，再讨论。前面 §1–§4 讲的是真实形态：B 实际是散落在多轮 user message 里、零零散散的几十上百个 tool_result，中间夹着 text / thinking / tool_use；C 也不是单一一条消息，而是若干轮 assistant 累积出来的判断 / 计划 / 代码改动。本节为了讲清"prefill 时 K/V 怎么算出来"、"释放 B 的 page 之后 C 还剩什么"这几件事，把散点抽象成连续的 A·B·C 三段：A = 早期 prefix，B = 要释放的旧 tool_result（视为一段连续区域），C = 后段 assistant 状态。这个简化丢掉了 B 散布、夹杂 text/tool_use 等细节——现实里这些由 §4 的 boundary / page 粒度自行处理；本节只关心抽象后的 KV 几何。请把 A/B/C 当成讨论工具，不当成数据结构。
图 3：cache_edits 与冷路径在 KV cache 内部的差别。同样起点（T0 prefill 出 KV(C | A, B)），触发压缩时冷路径整段重算，C 变成 KV(C | A, [cleared])，B 的影响全失；cache_edits 只释放 B 的 page，KV(C | A, B) 原值保留，B 的影响通过 C 隐式带给后续 token D。

5.1 cache_edits 不重算任何 KV

这是和冷路径最直接的差别。冷路径改了 messages，prefix 从置空处起破，服务端 cache miss，要把 A 之后的所有 token 重新 prefill 一遍——长 session 上这是 100K+ token 的全量 attention 计算。cache_edits 不改 messages 一个字节，A 段、C 段的 KV 是 T0 那次 prefill 算出来的原值，服务端只做了一件事：把 B 对应的 page 从 page_manager 里释放。没有任何 K/V 被重算。

这一点对应到 §4 的代码注释——服务端 page release 是已有的 turn-to-turn 机制，cache_edits 只是给它加了一条按 cache_reference 触发的入口。所以 cache_edits 在服务端的"成本"几乎可以忽略：标记几个 page 为 released，不动任何 attention 计算。

5.2 C 的 K/V 凝固着 prefill 时见过 B 的状态

这一点是 cache_edits 最值得理解的部分，也是它和"普通的删 = 信息全丢"的根本差别。

Transformer prefill 阶段是个有顺序的过程：A 先过 attention 算出 KV(A)；然后 B 过 attention，每个 B token 的 Q 都能 attend 到 A，所以 KV(B) 是"看着 A 算出来的"；最后 C 过 attention，每个 C token 的 Q 都能 attend 到 A 和 B，所以 C 的每一个 K/V 向量是基于"看得见 A、看得见 B"的语境算出来的。形式化写出来：

KV(C | A, B)  ≠  KV(C | A)

这两者的差别不是"附加信息"那种概念上的差别，而是 K/V 向量本身在数值层面就不同——C 的每个 token 在 prefill 时，attention 一定会去看 B 的 K/V，看完之后形成的 hidden state 进而决定 C 自己的 K/V。B 的影响在 prefill 那一刻就被烧进了 C 的 K/V 数值里，没法剥离开。

cache_edits 释放的是 B 的 page，不是 C 的 page。所以保留下来的 KV(A) 和 KV(C | A, B) 都是 T0 prefill 出来的原值——C 仍然是"消化过 B 的那个 C"。后续新 token D 进来 attention 时：

  • 看不到 B 的 KV pages（已 released）
  • 看得到 KV(A) 和 KV(C | A, B)
  • 而 KV(C | A, B) 在数值层面就携带着 B 当时对 C 的影响

结果就是：原始 B 的细节模型查不到了，但 C 里"看过 B 时形成的判断、根因、计划"仍在。这是个挺巧妙的"压缩同时不丢历史影响"——并不是 cache_edits 主动设计了什么"信息保留"机制，而是 prefill 顺序天然形成的副作用，cache_edits 只是没去破坏它（C 的 page 没动）。

对应到 coding agent 的常见模式："我跑了 grep，结果如下（B：2 万行）。我从中看到根因是 X，已经定位到文件 Y 的第 Z 行（C：100 字）。"——B 的原文从 KV cache 释放掉了，但 C 当年算出来时是看着这 2 万行 grep 输出形成的"根因 X、文件 Y、第 Z 行"，这些判断在 C 的 K/V 里被凝固下来。模型后续工作仍能基于 C 推进。

把 cache_edits 放回到压缩方案的谱系里看一眼：

prefix hash从首处改动起破从摘要插入处起破不破
是否要重算 KV整段重算整段重算不重算
被压缩内容对 C 的影响丢失（C 重算时看不见）丢失（C 是从摘要重新 prefill 出来的）保留（KV(C \| A, B) 是 T0 原值）
触发条件cache 已凉上下文逼近上限tool_result 数量超阈值

核心红利汇成一句：cache_edits 是同时拿到"不改 messages（cache 不破）+ 不重算 KV + 被删部分通过 C 的 K/V 隐式留下影响"三件事的压缩方案。普通方案二选一已经不容易，三件事同时拿到的代价是必须有 first-party stack 才能做（§6 展开）。

5.4 system prompt 在 prompt 层放大这个机制

5.2 讲的红利有一个隐含前提——C 真的吸收了 B 的关键内容。如果 prefill C 那一刻，模型只是草草看了一眼 B 就略过，C 的 K/V 里就承载不了多少 B 的信息。删 B 后 C 看起来还在，但里面其实空空。

有意思的是，Claude Code 的 system prompt 里有一段专门为这件事配合：

When working with tool results, write down any important information you might
need later in your response, as the original tool result may be cleared later.

这句话翻译过来是："处理工具结果时，把后面可能要用到的关键信息明文写进你的回复——原始 tool result 之后可能被清掉。"它在 prompt 层主动诱导模型在 prefill C（assistant 回复）的时候多消化 B（tool result）的内容、多写明确的总结判断。消化得越扎实，C 的 K/V 里凝固的 B 的影响就越多，cache_edits 后续删 B 的代价就越小。

这是机制设计上一个巧妙的配合：服务端的 cache_edits 提供"压缩同时不丢影响"的物理基础，prompt 层的这条 instruction 让"C 吸收 B"这件事在每一轮被持续放大。两端配合起来，长 session 跑下来 cache_edits 才能真正发挥效果——而不只是"理论上 C 有 B 的痕迹，实际上痕迹很浅"。

六、这是 Anthropic 内部能力，不是公开 API 代码已证实

客户端开关有三层硬条件：provider === 'firstParty'（必须直连 Anthropic API，Bedrock / Vertex / OpenRouter / 自建 proxy 走不通）+ querySource === 'repl_main_thread'（仅 REPL 主线程，子 agent 不开）+ CACHE_EDITING_BETA_HEADER（公开 build 里这个常量是空字符串，ant build 才有具体值）。三层加在一起意思很明确：cache_edits 是 Anthropic first-party stack 上的内部 beta 能力，不在公开 prompt caching 文档里。第三方 SDK / 兼容层即使发同样形状的 cache_edits block，目标服务端没有对应处理逻辑——具体表现是被忽略、报错还是按 raw prefix 兜底，得实测。

七、整体图景与差异化优势：如果推测大致正确，意味着什么

如果 cache_edits 真的按上面推测的方式工作，它的特殊之处是同时拿到了三件普通压缩拿不全的红利——不改 messages（cache 不破）、不重算 KV、被删部分通过 C 的 K/V 隐式留下影响。任何走"改 messages → cache miss → 重算"路线的普通压缩都拿不到这三件事；而走"靠摘要保留信息"路线的方案，C 的 K/V 是基于摘要重新算出来的，B 的影响也无法被原本的 prefill 数值层凝固下来。cache_edits 是同时满足这三件事的唯一已知做法，前提是必须有 first-party 服务端栈。

这套机制的代价相对清楚：必须 first-party（依赖 Mycro 的 page_manager）、必须 beta header（未公开 API）、必须接受"原始 tool_result 不可回查"。收益也比较清楚：cache 还热的场景下也能持续压缩旧 tool_result，长 session 跑下去既不破 cache 经济性、又不让模型完全失去过去做过的判断。

这或许会成为 Anthropic 的 model × agent harness 护城河

用现在比较主流的说法描述：cache_edits 是一个典型的 model × agent harness 协同优势——单看模型层不构成优势，单看 agent 框架也不构成优势，必须两端配合才能拿到。

具体到这个机制：

  • Claude 模型那一端支持 cache_edits 这个特性——服务端 page_manager 里有按 cache_reference 主动释放 page 的入口，并保证 release 之后后续 token 的 logical position 不受影响、attention 计算正常进行
  • Claude Code 这个 agent harness知道怎么用——会给 tool_result 标 cache_reference、会按阈值生成 cache_edits 块、会做 pin / 每轮重发，还在 system prompt 里通过"先把要紧的事记下来"那条 instruction 持续放大效果

少哪一端都不行：

  • Claude Code + 别家 LLM：在 Claude Code 里把模型换成 GPT / Gemini / 开源模型，cache_edits 块发过去对方服务端不认识——OpenAI、Bedrock 上的 Claude、自建 vLLM 都没有 page_manager 这一层。Claude Code 的客户端协议在没有相应服务端支持时只能退化成普通 prompt cache，cache_edits 那部分能力直接消失。
  • Claude 模型 + 别家 agent harness：在 Cursor / Aider / 自建 agent 里调 Anthropic API 直连 Claude，cache_edits 这个特性虽然服务端是有的，但客户端不发这种格式的请求、不知道怎么标 cache_reference、不知道怎么 pin / 重发——服务端有这能力也用不上，长 session 仍然会被旧 tool_result 拖死。

两端都是 Anthropic 自己做的（Claude 模型 + Claude Code），才能拿到这个完整能力。这就是典型的 model × agent harness 护城河：不是单一模型能力的领先，也不是某个工具好用，而是"模型支持的特性 + 客户端能用上这些特性"两件事必须捆绑才能复制。第三方接入方拿不到完整能力，要复制必须同时做模型和 agent harness 这两件事。

对 Anthropic 来说，这种护城河比单纯的模型能力领先更稳固——模型能力的差距追得上（OpenAI、DeepSeek、Google 都在追），但"模型 + harness 协同"的差距追起来代价高得多，因为这要求同时在两条产品线上做投入。Claude Code 越是把 agent harness 做厚（cache_edits 只是其一，背后还有 microcompact、context collapse、buddy 等等机制），这个护城河就越深。

当然这一切的前提是推测大致正确。如果 cache_edits 实际效果远不如预期（比如 C 对 B 的吸收不够扎实、删 B 后模型行为明显劣化），那这条护城河就不成立。

以上都是基于代码 + 一段注释的合理推测。欢迎大家在评论区交流：cache_edits 是不是这样工作的？这种 model × agent harness 的协同优势，会不会真的成为 Anthropic 的护城河之一？
