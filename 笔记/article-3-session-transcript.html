Claude Code session 存储拆解：harness 一直在变（崩溃、升级、换代），对话凭什么不变？

Anthropic 在 Managed Agents 一文里讲过两句很有意思的话。

第一句是关于崩溃的：

"Nothing in the harness needs to survive a crash."

翻译过来——跑 Claude Code 的进程随时可以死掉。崩溃、被 OOM kill、强制重启都行，对话状态不会丢。新进程拉起来就能从中断处接着干。

第二句是关于未来的：

"We can't predict what specific context engineering will be required in future models."

翻译过来——上下文怎么压缩、怎么裁剪、system prompt 怎么拼，这些都是会变的。今天的最优解不是明天的最优解，Anthropic 自己也不知道一年后会怎么做。

这两句话讲的是同一件事：harness 是个会变的东西。它会因为崩溃被替换、因为 CC 升级被替换、因为下一代模型被替换、因为压缩算法演进被替换。如果想让用户不为这些变化付代价（不丢历史、不停 session、不做迁移），唯一的办法就是把"会变的部分"和"必须长存的部分"在架构上彻底分开。

本文拆解的是 Claude Code 怎么划的这条边界——具体落地就是那个 append-only 的 JSONL 文件：

~/.claude/projects/<project-hash>/sessions/<sessionId>.jsonl

这条边界划完之后，下面四种"harness 变化"对用户都透明：

  • 进程崩溃 → 新 harness wake(sessionId) 读 JSONL，状态零丢失。
  • CC 升级 → 新版 harness 用新规则现场组装 prompt，旧 session resume 立刻吃到改进（修过的 bug、调过的 tone 全部生效）。
  • 压缩 / 上下文工程演进 → 直接用新策略重读旧 JSONL，无需任何迁移。
  • 模型换代 → 新 harness 按新 model 的 context 习惯重组上下文，session 文件本身不动。

四种场景的共性都是：harness 在变，session 不变。本文会看到：

  • 这条边界具体怎么划——五条设计哲学（§1）；
  • JSONL 物理上长什么样、文件布局怎么排（§2、§5）；
  • 写入是怎么做的、压缩之后旧历史去哪儿、rewind / fork 又是另一回事（§3、§4、§6）；
  • 最后从设计权衡的角度看——为什么 Anthropic 选了 append-only JSONL 而不是数据库或快照（§7）。

一、设计哲学：持久真相 vs 工作内存的分离

这是整套设计的总纲。一图说完：

图 1：JSONL 是档案馆，mutableMessages 是工作台。压缩、microcompact、占位替换都只动右边，左边永远是事件全集。

下面五点来自 Anthropic 的 Managed Agents 一文，也是仓库代码这套机制的"所以然"。

1.1 Session 是"外化的上下文对象"

"The session is an append-only log of everything that happened and functions as a context object that lives outside Claude's context window."

JSONL 文件不是服务于当前 API 调用的"工作内存"，而是一个独立于模型上下文窗口之外的历史档案馆。运行时内存里的 mutableMessages 负责即时的 API 交互；JSONL 负责忠实地记录一切，哪怕某些内容已经从当前 API 上下文中被裁剪掉。

1.2 Harness 是牲畜，不是宠物（Cattle, not pets）

"Nothing in the harness needs to survive a crash."

因为 session log 在 harness（query.ts / QueryEngine.ts / REPL）外面，所以运行进程完全可以随意崩溃、重启、替换。新的 harness 只需要 wake(sessionId)，调用 loadTranscriptFile 把 JSONL 读回来，就能完整恢复状态。代码里每一轮用户输入、assistant 输出、工具结果都实时追加到 JSONL，正是这种"进程可随时死去"的底气来源。

1.3 持久化存储与上下文工程解耦

"We can't predict what specific context engineering will be required in future models."

Anthropic 把边界划得很清楚：

  • Session（JSONL）只保证"所有事件都可恢复"。它不做任何 smart 的压缩或筛选，只 append。
  • Harness 承担所有上下文管理策略：组织、缓存、裁剪、compaction、microcompact、reactive compact。

这意味着，如果未来有更好的上下文工程方法，可以直接重放 JSONL 重新组织，无需改变持久化格式。代码里 compaction 不修改 JSONL、只修改"内存中发给 API 的视图"，正是这一哲学的直接体现。

1.4 API system prompt 不持久化：解耦的另一面

§1.3 讲的是 harness 在"事件出去给模型"这条路径上的自由——可以任意 compact、microcompact、按需筛选。§1.4 讲解耦的另一面：harness 每轮拼出来要塞给模型的 system prompt（CC 版本号、git status、CLAUDE.md、动态段、工具列表等），也全都不写进 JSONL。

src/context.ts 每轮请求前现场组装一份新的 system prompt，src/services/api/claude.ts 直接传给 Anthropic SDK，用完即弃。JSONL 里 type: "system" 的消息是终端 UI 元数据（api_metrics、compact_boundary、api_error），与 API system prompt 完全无关。

为什么这一刀切得这么干净？还是 §1.3 那句话：Anthropic 不能预测未来 context engineering 需要长什么样子。

如果 system prompt 被持久化进 JSONL，相当于把"现在认为正确的 prompt 拼装方式"冻结到磁盘。任何未来改动都会卡在两难：

  1. 让旧 session 永远用旧 prompt——用户体验随版本越拉越差，bug 修了等于没修；
  2. 写迁移脚本批量改写历史 JSONL——破坏 append-only 的崩溃安全保证，还要为每次 prompt 改动维护 migration。

把 system prompt 留在工作内存、每轮重新组装，三个具体好处自然就来了：

  • CC 升级：旧 session resume 立刻吃到新版 prompt（修过的 bug、调过的 tone、新增的 tool 全部生效），而不是冻结在 session 创建那一刻。
  • CLAUDE.md 中途改动：会话进行到一半时改项目根目录的 CLAUDE.md（加了新规约），下一轮自动重读注入，不用重启 session。
  • git status 持续刷新：会话期间 commit / 切分支 / 改文件，每轮重新拉一次状态，模型看到的是当下而不是开局快照。

但这些好处都是"派生品"，不是源命题。源命题是这条边界划分本身：

API system prompt 反映的是 harness 当下认为该说的话；session 反映的是已经发生过的事实。前者属于"can change"，后者属于"must not change"。把两类东西塞进同一份持久化里，就是把可演进性和可恢复性绑死。

Anthropic 选择把它们分开——session 严格记录事件，harness 永远按最新规则现场组装。这条边界划完之后，prompt 怎么改、模型怎么换、上下文工程怎么演进，都不再绑架持久化格式。

1.5 通过 getEvents() 任意选择历史切片

因为 JSONL 是完整、不可变的，harness 可以在恢复时灵活地"读取子集"——跳过 compact_boundary 之前的旧历史、从某个 leaf 节点往回追、或加载 sidechain 的 agent 子对话。文件是单一真相源，读取策略可以千变万化。

二、核心定位与文件布局

每个 session 有一个仅追加（append-only）的主 JSONL 日志文件：

~/.claude/projects/<project-hash>/sessions/<sessionId>.jsonl

它是会话的唯一持久化真相源，用于进程崩溃或退出后通过 --resume / --continue 恢复完整状态。

2.1 子 agent（Sidechain）的独立文件

子 agent 的内部对话不写主文件，而是写到旁链（sidechain）文件中：

~/.claude/projects/<project-hash>/sessions/<sessionId>/subagents/agent-<agentId>.jsonl
  • 旁链消息带有 isSidechain: true 和 agentId 字段。
  • 主 session resume 时不加载旁链文件，子 agent 的聊天记录对主链透明。
  • 子 agent 恢复（如用户显式点击继续）时，通过 getAgentTranscriptPath(agentId) 拼出路径，单独读取。

2.2 Fork Session 的新文件

--fork-session 不接管原 JSONL，而是保留启动时生成的新 sessionId，由 useLogMessages 在 REPL mount 时把旧消息逐条 recordTranscript 写入新文件。每条消息都会重新 stamp（sessionId、timestamp、cwd 等覆盖为 fork 后的值），确保 content-replacement 等元数据的 sessionId 键一致。

2.3 REPL 交互：从 query 到 JSONL 的数据流

交互 CLI 下，带 tool_use / tool_result 的 assistant、user 消息与普通消息走同一条管道：query() 只负责 yield；React state 在 REPL.tsx 的 onQueryEvent → handleMessageFromStream 回调里 setMessages；messages 变化触发 useLogMessages 的 useEffect，再 recordTranscript 追加 JSONL。

图 2：query.ts 是事件生产方，REPL.tsx 是消费/调度方，sessionStorage.ts 落盘。三方解耦，串起来才是完整数据流。

读图要点

  1. 三个框对应三个文件：REPL.tsx（调用方）、query.ts（事件生产方）、sessionStorage.ts（落盘）。
  2. query() 是 async generator，定义在 query.ts，由 REPL.tsx 的 for await...of 驱动消费——红色粗箭头表达跨文件调用。
  3. handleMessageFromStream 定义在 utils/messages.ts，但在 REPL 的回调里被调用，所以节点放在 REPL 框内。
  4. handleMessageFromStream 不直接调 setMessages，而是通过 onMessage 回调间接调用。stream_event（token 增量）只更新响应长度，不调 onMessage；只有完整消息（assistant / user / progress / compact）才走 onMessage → setMessages。
  5. setMessages → useLogMessages → useEffect → recordTranscript 是 React 响应式链：messages state 变化触发 hook，hook 内 useEffect 调 recordTranscript 写盘。

三、写入模型：仅追加，不修改历史

3.1 写入器

src/utils/sessionStorage.ts 中的 TranscriptWriter 负责写入：

  • 使用 fs.appendFile 批量追加新行。
  • 带内存缓冲队列和定时 flush（默认异步批量写），不阻塞主线程。
  • 日常对话运行时只写不读；内存中的 mutableMessages 是运行时真相源。

3.2 Compaction（上下文压缩）与日志的关系

无论发生哪种压缩，已写入的 JSONL 行不会被修改或删除：

  • MicroCompact：仅把旧工具输出替换为占位符发送给 API，原始内容仍留在 JSONL 中。
  • 传统 API 摘要压缩 / Session Memory Compact：在内存里生成摘要，然后插入一条 compact_boundary 边界标记。resume 时通过边界标记跳过前面的旧历史，但文件本身不会重写。
唯一例外是 removeMessageByUuid，用于清理失败的流式消息孤立记录。它会做尾部 truncate + write，触发场景极少。

3.3 Fork Session 的写入

--fork-session 的写入与普通 resume 不同：

维度普通 resume（--resume）Fork resume（--fork-session）
Session ID复用旧的保留启动时生成的新 ID
JSONL 文件接管原来的（adoptResumedSessionFile）新文件（getTranscriptPath() 按新 ID 推导）
消息复制已经在文件里，无需复制useLogMessages 在 REPL mount 时逐条 recordTranscript 写入
stamp 处理原样保留每条消息重新 stamp（sessionId / timestamp / cwd 覆盖为新值）

为什么必须重新 stamp？如果不覆盖 sessionId，新 JSONL 中的消息会带着旧 sessionId，而后续写入的 content-replacement 元数据是新 sessionId，导致 loadFullLog 按 sessionId 查找 replacement 时 miss——工具结果被误分类为 FROZEN，缓存失效。

四、消费场景：何时读取这个文件

场景读取方式说明
启动恢复（--continue、--resume）loadConversationForResume → loadTranscriptFile全量或按需解析 JSONL，沿 parentUuid 重建对话链
列表展示（/resume picker）loadSameRepoMessageLogs / loadAllProjectsMessageLogs先纯 stat 扫描，再对候选会话读 head/tail（约 16KB）提取标题和摘要

4.1 loadTranscriptFile 的加载策略

  • 小文件（< 5MB）：直接全量读取。
  • 大文件（> 5MB）：利用 compact_boundary 做前向跳读，跳过 pre-boundary 的过期内容，只保留 post-boundary 的消息和元数据。
  • 然后通过 buildConversationChain 从最新 leaf 消息沿 parentUuid 往回追，重建完整对话链。

4.2 为什么 JSONL 物理是 DAG，逻辑是单链

正常对话时，每条消息的 parentUuid 指向上一条，文件里确实是个链表。但 rewind（回退）会让它变成有向无环图（DAG）。

例如用户 rewind 到 B 后重新发了问题 E，append-only 不删旧数据：

图 3：rewind 让文件变成 DAG。死分支（C → D）物理保留，逻辑被丢弃。

buildConversationChain 恢复时，先从所有 terminal 消息（没有 child 的节点）中找到最新的 leaf（E），然后沿 parentUuid 往回追溯到 root。死分支 C → D 被自然丢弃。物理存储是 DAG，逻辑恢复是单链。

其他产生分支的情况：

  • Fork session：复制现有链到新 session 继续
  • Snip（删除消息）：applySnipRemovals 重连 parentUuid，被删的链段物理保留
  • 并行 tool_use 拆分：streaming 时一个 assistant 响应拆成 N 条消息，兄弟块通过 message.id 关联

六、写入示例：正常对话与压缩场景

下面用简化后的 JSONL 行展示两个典型场景，帮助理解文件里实际会出现什么内容。每行都是独立 JSON，按时间顺序追加。

6.1 场景 A：正常 Agent 工作（一轮工具调用）

用户问"帮我列出当前目录的文件"，Claude 调用 BashTool 执行 ls，然后返回结果。

这一轮的 yield 流程与 JSONL 写入关系：

  • 用户发送消息 → REPL.tsx 直接 setMessages + recordTranscript → JSONL 写入第 1 行（user）

  • yield 完整 assistant 消息（含 tool_use block）→ JSONL 写入第 2 行（assistant）
  • 工具执行完成，yield user 消息（含 tool_result block）→ JSONL 写入第 3 行（tool_result）
  • 递归进入下一轮 API，再 yield stream_event → 不写 JSONL
  • 最后 yield assistant 最终回复 → JSONL 写入第 4 行（assistant）

要点

  • 一次 yield 只产出一个事件，postCompactMessages 是用循环逐个 yield message 的。
  • stream_event（token 增量）yield 时不写 JSONL，只更新响应长度；只有完整消息才走 onMessage → setMessages → recordTranscript。
  • 所有消息通过 parentUuid 形成单链表：u-001 → a-002 → u-003 → a-004。
  • usage.input_tokens 在每条 assistant message 上记录，是 finalContextTokensFromLastResponse 读取的数据源。

6.2 场景 B：触发压缩（AutoCompact）后

假设上述对话又进行了 20 轮，上下文膨胀到 180K tokens，触发了 autocompact。

这一轮的 yield 流程：

  • deps.autocompact() 成功返回 compactionResult
  • query() 用 buildPostCompactMessages(result) 组装出 4 条消息
  • 循环 yield 这 4 条消息，每条独立消费、独立写盘
  • 旧历史（前面 20+ 轮）不会被删除或修改

七、设计权衡

把前面这些机制串起来看，会发现 Anthropic 在三处都选了"看起来更笨"的方案，但每一个选择背后都有非常具体的工程理由：

选择原因
每条消息自带 session 级字段 由于 append-only 无法共享文件头，只能用磁盘空间换写入性能。1000 轮会话会把 sessionId / cwd / version 重复写 1000 次——但每次写都是无状态、无锁的 fs.appendFile，进程崩了也不会留下半行残缺数据。
compaction 不删旧数据 文件只增不减，通过 compact_boundary 在读取时跳过旧历史。这换来两个保证：(1) 崩溃安全——即使压缩过程中进程死掉，已写入的数据仍完整可用；(2) 历史可重放——未来如果换一种压缩策略，可以基于 JSONL 重做，不用搬数据。
元数据重复 re-append 在 compact 前后和退出时，把 custom-title、tag、last-prompt 等重新刷到文件尾部，确保它们落在 readLiteMetadata 扫描的 tail 窗口（约 16KB）内，否则 resume 列表会看不到。这是"读取速度"和"写入冗余"之间的故意倾斜——picker 必须秒开。

把这三个权衡反过来看，就是 Anthropic 这套 session 设计的核心命题：

磁盘很便宜，进程很脆弱，未来很不确定。所以——文件越笨越好（只 append），harness 越聪明越好（任意压缩、裁剪、重组），两者之间用 JSONL 这层简单格式划清边界。

这正好回到开头那两句话。harness 是会变的——崩溃换进程、升级换版本、换代换实现、改 prompt 换组装方式——所有这些"变"都被关在 harness 边界内；JSONL 是不变的，append 进去的事件永远在那里、什么都不删。把"会变"和"不变"用一份 append-only 文件干净切开，是 Anthropic 这套设计最核心的一刀。
